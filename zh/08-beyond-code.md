# 代码之外

成为一名优秀的软件工程师，不只是写出能运行的代码。而是写出他人（包括未来的你）能够理解、维护并在其基础上继续构建的代码。它关乎清晰地沟通、深思熟虑地贡献，并在你所参与的生态系统中做一个好公民——无论是开源还是专有软件。

# 单向沟通

软件工程的很大一部分是写给那些不具备你当前上下文的人看的：后来加入的团队成员、接手你代码的维护者（maintainer），或者六个月后的你自己——那时你已经忘了当初为什么做出某个特定选择。对于所有这类写作，一条关键建议是：你的目标是捕捉并传达*为什么*（why），而不仅仅是*是什么*（what）。“是什么”往往不言自明，而*为什么*是来之不易的知识，很容易湮没在时间里。

工程师之间最常见的沟通形式（除了代码本身）可能就是代码注释（code comment）了。就我个人经验，很多代码注释都毫无用处。但它们并非必须如此！好的注释解释代码本身无法表达的东西：某件事*为什么*以某种特定方式来做，而不是它*如何*工作（那是代码本身展示的）。好的注释能省下数小时的困惑，而糟糕的注释只会增加噪音，甚至更糟——误导读者。

几乎总是值得写的注释类型：

* **TODO**：标记未完成或未打磨的代码，但要留下足够的上下文，让别人明白还有什么没做、为什么被推迟。“TODO：优化”毫无用处；“TODO：这个 O(n²) 循环在 `n<100` 时没问题，但如果要扩展规模就需要加索引”则具有可操作性。
* **引用来源**：当代码实现了论文中的某个算法、改编自别处的代码，或者编码了文档中规定的行为时，链接到外部来源。使用永久链接（permalink）。并注明与参考来源的任何偏离。
* **正确性论证**：解释*为什么*非平凡的代码能产生正确的结果。代码展示步骤；注释解释这些步骤为什么成立。
* **来之不易的教训**：如果你花了 30 多分钟调试某个问题，而修复方法是一段不那么显然的“咒语”，那就把它记录下来。过去的你没意识到它会被需要；未来的读者也不会意识到。
* **常量的理由**：魔数（magic number）值得解释。为什么是 1492？为什么是 16 位？它是随机选择的、从测试中推导出来的，还是正确性所要求的？即使是“随意选择的”也是有用的信息。
* **承重的选择**：如果正确性依赖于某个看似无害的实现细节（例如“必须用 BTreeSet，因为下面的代码依赖迭代顺序”），请明确指出。
* **“为什么不”**：当你刻意避开显而易见的做法时，解释原因。否则日后有人会去“修复”它，然后把事情搞砸。

README（你有 README，对吧？）也是与其他开发者的常见第一次接触点。一份好的 README 会立即回答四个问题：这是做什么的？我为什么要关心？我该怎么用？我该怎么安装？按这个顺序。把它组织成漏斗形：顶部放一句话简介，也许再加一个可视化演示，让人几秒内就能判断这能不能解决他们的问题，然后逐步增加深度。先展示用法，再展示安装——人们想先看看能得到什么，再决定投入安装步骤。

提交信息（commit message）是另一种常被忽视的“为他人写作”。它们常被写成“修了某某”或“加了某某”，虽然在某些情况下这可能足够了，但人们很容易忘记，它们构成了代码库*为什么*如此演进的历史记录。当有人（包括你自己！）运行 `git blame` 试图理解一个令人困惑的变更时，好的提交信息应该能给出答案。

一般来说，提交信息的正文应该回答：

* 是什么问题迫使了这次变更？
* 你考虑过哪些替代方案？
* 有哪些权衡或影响？
* 这个做法有什么可能令人意外的地方？

> 显然，你应根据复杂度来调整详略。一行的错别字修复只需要一个主题行。一个花了数小时调试的微妙竞态条件修复，则值得用几段文字来解释问题和解决方案。

对于复杂的变更，遵循“问题 → 解决方案 → 影响”的结构会很有用：先写出催生变更的因素或局限性，然后解释改了什么以及关键的设计决策，最后列出值得注意的后果（正面和负面的）。最后这部分尤其重要；真正的工程在于权衡各种考量，而记录下某个权衡是有意为之，可以避免未来的开发者以为你忽略了这个问题。

大语言模型（LLM）*可以*帮助撰写提交信息。然而，如果你只是把变更丢给它，让它为这个变更写提交信息，那么 LLM 只能接触到*是什么*，而接触不到*为什么*。由此产生的提交信息将主要是描述性的（与我们想要的正好相反！）。如果你当初就是用 LLM 帮你完成这个变更的，那么在同一个会话中让 LLM 来写提交信息可能是个好得多的选择，因为你与 LLM 的对话本身就是关于该变更的丰富上下文来源！否则，或者除此之外，一个有用的技巧是明确告诉 LLM 你想要一条聚焦于“为什么”的提交信息（以及上面提到的其他要点），然后*让它反过来向你询问缺失的上下文*。本质上，你就像是编码智能体的一个 MCP“工具”，供它“读取”上下文。

随着你的变更越来越复杂，还要确保在逻辑上拆分提交（`git add -p` 是你的好帮手）。每个提交应代表一个连贯的变更，可以被独立地理解和审查。不要把重构和新功能混在一起，也不要合并无关的缺陷修复（bug fix），因为这会让“哪些变更修复了哪些问题”的故事变得混乱，而且几乎肯定会拖慢对你变更的最终审查。它还能通过 `git bisect` 给你“超能力”，但那就是另一个故事了。

> 在你开始更认真地对待技术写作、并更广泛地使用它时，有一点提醒：一定要尊重读者。一旦开始写，很容易过度解释，但你必须克制这种冲动，以免读者干脆*什么都*不看你写的内容。解释“为什么”，相信他们能自行弄清楚适用于他们场景的“怎么做”。

# 协作

作为工程师，我们可能有很大一部分工作时间是独自坐在键盘前写代码，但我们也有相当多的时间花在与他人沟通上。这些时间通常分为协作和教育两部分，而在这两方面投入并变得更好，回报是巨大的。

## 做贡献

无论你是提交一份缺陷报告（bug report）、贡献一个简单的缺陷修复，还是实现一个庞大的功能，都值得记住：用户通常比贡献者多好几个数量级，而贡献者又比维护者多一个数量级。因此，维护者的时间是极其供不应求的。如果你想提高你的贡献能开花结果的可能性，就必须确保你的贡献具有高信噪比，值得维护者花时间去看。

例如，一份好的缺陷报告通过提供理解并复现问题所需的一切来尊重维护者的时间：

* **环境**：操作系统、版本号、相关配置
* **你的预期**对比**实际发生的情况**
* **复现步骤**：要具体。“点击按钮”就不如“以管理员身份登录，在 /settings 页面点击 Submit 按钮”有用。
* **你已经尝试过什么**：这可以避免重复的建议，也表明你已经做了一些调查

> 如果你发现了安全漏洞，不要公开发布。先私下联系维护者，给他们合理的时间修复后再披露。许多项目有 SECURITY.md 文件或类似文件用于此目的。

**务必先搜索已有的 issue。** 你的缺陷或功能请求可能已经有人报告过了，向已有的讨论中补充信息远好过创建重复项。更不用说，这也能为维护者减少噪音。

最小可复现示例（minimal reproducible example）是黄金般的存在，如果你能弄出一个的话。它们为维护者节省大量的时间和精力，而可靠地复现缺陷往往是修复它最难的部分。更不用说，你在隔离问题上投入的精力通常也能帮你更好地理解它，有时还能让你自己找到修复方法。

如果你没有立刻收到回复，请记住维护者往往是时间有限的志愿者。如果你在等他们回复，几周后礼貌地跟进一次是可以的；每天催促则不行。同样，“我也是”之类的评论，或者只是把某些终端输出复制粘贴过来的缺陷报告，对于推动你的 issue 往往是有净负面效果的。

如果你想贡献代码，你还需要熟悉贡献指南。许多项目有 `CONTRIBUTING.md` ——请遵循它。你通常还想从小处着手；修复错别字或改进文档是很好的首次贡献，因为它能帮你了解项目的流程，而不必在内容上来回拉扯太多。

> 检查项目使用的是什么许可证（license），因为你贡献的任何代码都将适用相同的许可证。特别要注意 copyleft 许可证（如 GPL），它要求衍生作品也必须开源，如果你碰它，可能会对你的雇主有影响！[choosealicense.com](https://choosealicense.com/) 上有更多有用的信息。

当你决定提交拉取请求（pull request，PR）时，首先要确保把你真正希望被接受的变更隔离开来。如果你的 PR 同时改动了很多其他无关的东西，审查者很可能会把它退回给你，让你清理干净。这类似于你应该把 git 提交拆分成语义相关的块。

在某些情况下，如果你有许多看似不相关的变更，但它们都是启用某个功能所必需的，那么提交一个包含所有这些变更的较大 PR 也许可以接受。不过在这种情况下，提交卫生（commit hygiene）就尤为重要，这样维护者可以选择“逐个提交”地审查变更。

接下来，确保把变更背后的“为什么”解释清楚。不要只描述改了*什么*——要解释*为什么*需要这个变更，以及*为什么*这是解决问题的好方法。你还应该主动指出变更中需要在审查里特别关注的部分（如果有的话）。根据 `CONTRIBUTING.md` 和你变更的性质，审查者可能还希望看到额外的信息，比如你所做的权衡，或者如何测试这个变更。

> 我们建议回馈（contribute back to）上游项目，而不是“fork”这个项目，至少作为首选方式是这样。Fork（在许可证允许的情况下）应该留给你想做的贡献超出原项目范围的时候。如果你确实 fork 了，务必注明原项目！

AI 让快速生成看起来像模像样的代码和 PR 变得无比容易，但这并不能免除你理解自己所贡献内容的责任。提交你无法解释的 AI 生成代码，会让维护者背上审查、甚至可能长期维护连作者自己都不理解的代码的负担。用 AI 来帮你定位问题并产出修复/功能是可以的，**前提是你仍然尽到应有的尽职调查**，把它打磨成值得接受的贡献，而不是把这项工作转嫁给（已经不堪重负的）维护者。

请记住，对维护者来说，接受一个 PR 意味着接受长期责任。在贡献者早已另谋高就之后，他们仍将长期维护这段代码，因此他们可能会拒绝那些出于好意但不符合项目方向的变更、增加他们不想维护的复杂度的变更，或者需求根本没有被充分记录下来的变更。作为贡献者，*你*有责任论证为什么接受这个贡献值得它带来的维护负担。

> 在收到对 PR 的反馈时，记住你的代码不是你本人！审查者是想让代码变得更好，而不是在批评你个人。如果你不同意，可以提出澄清性的问题——也许你能学到东西，也许他们能。

## 审查

你可能觉得代码审查是资深开发者做的事，但你被要求审查代码的时间很可能比你预期的早得多，而且你的视角很有价值。新鲜的眼睛能发现经验丰富的开发者忽略的东西，而对代码不太熟悉的人提出的问题，往往能揭示那些本应被记录下来或简化的假设。

审查也是最快的学习方式之一。你会看到别人如何解决问题，学到模式和惯用法，并对什么让代码可读建立起直觉。除了个人成长之外，审查能在缺陷进入生产环境之前抓住它们，在团队中传播知识，并通过协作提升代码质量。它们绝不仅仅是官僚式的开销。

好的代码审查是一项需要长期磨练的技能，但有一些技巧能让它们更快地变得好得多：

* **审查代码，而不是人**：“这个函数令人困惑”对比“你写了令人困惑的代码”。
* **优先给出可操作的意见**：“你能把这些全局变量替换成一个配置数据类（dataclass）吗”比“这里别用全局变量”更容易落实。
* **提问，而不是下命令**：“如果这里 X 为 null 会怎么样？”比“处理一下 null 的情况。”更能引发讨论。
* **解释“为什么”**：“考虑在这里用一个常量”不如“考虑在这里用一个常量，这样我们就能根据环境轻松调整超时时间”有用。
* **区分阻塞性问题和建议**：明确哪些必须改，哪些只是偏好问题。
* **认可做得好的地方**：指出巧妙的解决方案或干净的实现令人鼓舞，也能让作者知道哪些做法应该继续保持。
* **知道何时收手**：贡献者的时间和耐心是有限的，把时间都花在处理所有吹毛求疵的小问题上并不总是最好的。把重点放在大问题上，事后再考虑自己顺手把这些小问题清理掉。

> AI 工具能发现某些问题，但它们无法替代人工审查。它们缺乏上下文，不理解产品需求，而且会自信地给出错误的建议。它们值得用作第一遍筛查，但不能替代深思熟虑的人工审查。

# 教育

作为工程师，我们的很多非编码时间都花在提问或回答问题上，也可能两者兼而有之：在协作中、与同伴的对话中，或者在努力学习的过程中。会问好问题是一项技能，它能让你更善于向任何人学习，而不仅仅是那些讲解得完美的人。Julia Evans 写过一些出色的博客文章，包括[如何提出好问题](https://jvns.ca/blog/good-questions/)和[如何获得对你问题的有用回答](https://jvns.ca/blog/2021/10/21/how-to-get-useful-answers-to-your-questions/)，值得一读。

一些特别有价值的建议是：

* **先陈述你的理解**：说出你认为自己知道的东西，然后问“对吗？”这能帮助回答者定位你真正的知识缺口。
* **问是非题**：“X 是真的吗？”可以防止跑题式的解释，而且通常也能引出有用的详细说明。
* **要具体**：“SQL 的连接是怎么工作的？”太模糊了。“LEFT JOIN 会包含右表中没有匹配的行吗？”则是可以回答的。
* **不懂就承认**：遇到不熟悉的术语，打断并提问。这反映的是自信，而不是软弱。同样，如果他们问了你不知道答案的问题，最好就说“我不知道”，还可以接着说“但我认为……”甚至“但我可以去查一下”。
* **不要接受不完整的回答**：不断追问，直到你真正理解。
* **先做一些研究**：基本的调查能帮你提出更有针对性的问题（不过同事之间随意的提问也没问题）。

记住：精心构思的问题会让整个社区受益。它们揭示了那些隐藏的假设，而其他人也需要理解这些假设。

> 注意，这条建议在与 LLM 沟通时同样适用！

# AI 礼仪

随着 LLM 和 AI 在软件工程中的使用日益普遍，与之相关的社会和职业规范仍在演变之中。我们在[智能体编码讲座](/2026/agentic-coding/)中已经涵盖了许多战术层面的考量，但它们的使用也有一些“更软性”的方面值得讨论。

其中第一点是：当 AI 对你的工作有实质性贡献时，**要披露**。这无关羞耻——而是关乎诚实、设定恰当的期望，并确保最终成果得到适当程度的审查。披露你在哪些*部分*使用了 AI 也是有价值的——“这整个东西都是纯靠感觉让 AI 写出来的（vibecoded）”和“我写了这个备份工具，并用 LLM 给网页前端做了样式”之间有实质性区别。例如，我们就用 LLM 帮忙撰写了部分讲义，包括校对、头脑风暴，以及生成代码片段和练习的初稿。

你也要遵循你所贡献的团队和项目在这方面的规范。有些团队对 AI 的使用有比其他团队更严格的政策（例如出于合规或数据驻留方面的原因），你不会想不小心触犯这些政策。公开透明地说明你的使用情况，有助于防止可能代价高昂的错误。

> 如果你希望在所做的工作中有所学习，请记住：让 AI 替你完成全部或大部分工作可能是自我挫败的；你学到的可能更多是关于提示（以及也许审查 AI 输出），而不是任务本身。尤其在学习阶段，重点可能在于旅途本身而非终点，所以用 AI“快速得到答案”是一个反目标。

一个相关的顾虑出现在面试和其他评估场景中。这些场景往往意在专门评估*你*的技能和能力，而不是某个 LLM 的。现在越来越多的公司允许你在面试中使用 LLM 和其他 AI 辅助工具，前提是让他们把这些交互作为面试的一部分加以观察（也就是说，他们也在评估你使用这些工具的技能！），但这仍然属于少数。如果你不确定某个特定任务是否允许 AI 辅助，就问！

> 不言而喻，如果某个评估场景明确要求不使用外部工具、不使用 LLM 等等，你就不应该使用它们。试图偷偷使用而不被抓到**迟早**会反噬你。

# 练习

1. 浏览一个知名项目的源代码（例如 [Redis](https://github.com/redis/redis) 或 [curl](https://github.com/curl/curl)）。找出讲座中提到的某些注释类型的例子：一个有用的 TODO、一个指向外部文档的引用、一个解释被避开做法的“为什么不”注释，或者一条来之不易的教训。如果那条注释不在那里，会失去什么？
2. 选一个你感兴趣的开源项目，看看它最近的提交历史（`git log`）。找一个带有好提交信息的提交——它解释了*为什么*做这个变更；再找一个只有弱提交信息的提交——它只描述了*什么*变了。对于弱的那个，看一下 diff（`git show`），然后试着按照“问题 → 解决方案 → 影响”的结构写一条更好的提交信息。体会一下事后重新拼凑必要上下文需要多少功夫！
3. 对比三个拥有 1000+ star 的 GitHub 项目的 README。它们是否同样有用？找出那些对你来说主要像噪音的东西，作为你以后自己写 README 时的借鉴。
4. 在你使用的某个项目上找一个未解决的 issue（如果有“good first issue”或“help wanted”标签的话，可以查看这些标签）。按照讲座中的标准评估这个 issue：它看起来是否重视维护者的时间，并包含调试它所需的所有信息？还是说你预计维护者可能需要和提交者来回好几轮提问才能触及根本问题？
5. 想一个你在所用软件中遇到过的缺陷（或者在某个 issue 跟踪系统里找一个）。练习创建一个最小可复现示例：剥离一切与该缺陷无关的东西，直到得到仍然能展示该问题的最小案例。写下你删掉了什么以及为什么删。
6. 在你熟悉的某个项目上找一个已合并的拉取请求，它有实质性的审查意见（而不只是“LGTM”）。通读整个审查。所有意见是否都同样有成效？如果你是这个 PR 的作者，收到那么多意见你会作何感想？
7. 去 Stack Overflow 上找一个你熟悉的技术领域的问题，它有一个高票答案。然后再找一个被关闭或被大量踩的问题。把它们与讲座中的建议对比；哪个问题会得到更好的回答，是否是可以预测的？
